Language documentation

Everything the votyer language can do, in one page. votyer is a small, readable language that compiles in the browser into a running retro 3D game. If you have ever written a config file, you can write votyer — and if you have ever written JavaScript, you will feel at home in its handlers.

§Introduction

votyer is a domain-specific language for retro HTML5 games. A votyer program describes four things: the world (game settings, the map), the things in it (items, enemies, the exit), the rules of the world, and event handlers that run when things happen. Everything else — the raycasting renderer, physics, audio, HUD, menus — is handled by the engine inside votyer.js.

The language is deliberately tiny. There are no classes, no imports and no async. There are blocks, a handful of commands, simple expressions and events. That keeps game scripts short enough to read top-to-bottom like a level design document, which is exactly the point. Most complete games fit in under 150 lines.

Under the hood, the runtime is a classic three-stage compiler: a lexer turns your text into tokens, a parser builds an abstract syntax tree, and an interpreter executes handler blocks against the live engine. Compile errors are reported with line and column numbers both in the browser console and on the canvas itself.

§Getting started

A votyer game is embedded in a normal HTML5 page. Load the runtime, then write your program inside a <script type="text/votyer"> tag. When the page loads, the runtime finds every votyer script and boots it automatically.

<!DOCTYPE html>
<html>
<head><meta charset="utf-8"></head>
<body>

<canvas id="game"></canvas>

<script src="votyer.js"></script>

<script type="text/votyer" data-canvas="#game">
game "Hello World" {
    size 800 500
}

map {
    "########"
    "#P.....#"
    "#......#"
    "########"
}
</script>

</body>
</html>

The data-canvas attribute tells the engine which canvas to render into. If you omit it, the runtime creates a canvas for you right after the script tag and styles it responsively. That is all the HTML5 integration you need — the rest of the page can be a normal website, so games can live inside blog posts, landing pages or documentation exactly like the demo on this site does.

No server required. Because there is no build step and no fetch at runtime, votyer games work from file://, from GitHub Pages, from any CDN, or even attached to an email as a single HTML file.

§Anatomy of a game

A votyer program is a list of declarations. Order does not matter — you can declare items before the map or after it. The compiler collects everything into a game blueprint before the engine boots, so you are free to organize the file however reads best for you. A typical layout looks like this:

game "Crystal Quest" { ... }   // 1. settings — size, colors, physics
palette { ... }                // 2. optional wall colors
map { ... }                    // 3. the world layout
item "crystal" { ... }         // 4. things that populate the world
enemy "guard"   { ... }
exit { ... }                   // 5. the way out
rules { ... }                  // 6. world-level cause and effect
on start { ... }               // 7. event handlers
on tick  { ... }

Comments use // for a single line and /* ... */ for blocks, just like JavaScript. Use them liberally — votyer files are meant to be read by humans and level designers, not only by machines.

§The game block

The game declaration sets the title and tuning of the whole game. Every setting is optional; anything you leave out falls back to a sensible retro default. The name in quotes is shown on the title screen, and the optional title setting lets you override the big display text separately.

game "Crystal Quest" {
    size 960 560        // canvas resolution in pixels
    title "CRYSTAL QUEST"
    sky #101426         // ceiling color
    floor #3d2b1f       // floor color
    fog 0.45            // 0 = clear view, 1 = claustrophobic
    fogcolor #0d1524    // new in 1.1 — atmosphere color
    speed 3.2           // player speed, tiles per second
    turn 2.8            // keyboard turn speed, radians per second
    fov 68              // field of view in degrees
    sensitivity 0.0022  // mouse look sensitivity
    minimap on          // show the minimap (toggle with M)
    texture on          // textured walls (off = flat retro shading)
    ceiling off         // new in 1.1 — open sky + stars
    detail 0.7          // new in 1.1 — render detail, 0.3 to 1
}
SettingDefaultWhat it does
size800 500Internal render resolution. The canvas scales to fit its container while keeping the chunky retro pixels.
sky / floornight blue / dirt brownColors of the ceiling and floor bands. Accepts #rgb or #rrggbb hex colors, with or without quotes.
fog0.4How quickly walls fade into darkness with distance. Higher values shorten the view distance for a moodier dungeon.
fogcolor 1.1the sky colorThe color distance fades into. Set it slightly darker than sky for caves, or bright blue for open-air maps.
speed3.0Player movement speed in tiles per second.
turn2.6Turning speed for the arrow keys, in radians per second.
fov66Horizontal field of view. Classic Wolfenstein-style values sit between 60 and 75.
minimap / textureonTurn the HUD minimap or the textured-wall renderer on or off. texture off falls back to fast flat-color shading.
ceiling / stars 1.1onceiling off replaces the ceiling with a gradient sky and a twinkling starfield (parallax by view angle). stars off removes just the stars.
detail 1.10.62Internal render resolution from 0.3 (fastest, chunky) to 1 (native, sharpest). The 3D view is rendered to a framebuffer and upscaled, so lower values run faster on weak hardware.

§Maps & palettes

The map block is the world itself — a list of quoted strings, one per row. It is the heart of every votyer game and the part you will edit the most. Treat it like ASCII art: walls are drawn with symbols, floors are dots, and creatures and objects are single letters placed on the floor.

CharacterMeaning
#A standard wall, rendered with the default stone color.
. or spaceWalkable floor.
PThe player start position and facing. If omitted, the engine spawns the player at the first open cell.
any letter you defineA spawn point for an item, an enemy or the exit — set with the char property. These cells are walkable.
palette charactersColored wall variants (see below). These are solid walls too.
any other symbolAnything else non-space is treated as a wall with an auto-assigned color, so you can freely use %, =, + and friends as decoration.

The palette block assigns colors to single characters, which become wall variants. This is how you build themed levels — brick red for the dungeon, alien purple for the vault, mossy green for the sewers:

palette {
    "1" #5a3b8f      // alien brick
    "2" #2f6f6a      // teal stone
}

map {
    "#########"
    "#P..1..2#"
    "#.#####.#"
    "#.......#"
    "#########"
}
Design tip. Rows may be different lengths — short rows are padded with floor — but the outer border must be sealed with walls, otherwise rays escape the world. The engine clamps out-of-bounds rays, so a leaky border looks odd rather than crashing. The tutorial ships a checker; steal it.

§Water & liquids new in 1.1

Water is the flagship feature of v1.1. Declare a water block, then paint tiles with ~ in the map. Water cells are fully walkable — the renderer draws them as a second surface with animated wave displacement, sky reflections that strengthen with distance, moving specular highlights and gentle ripple bands, all computed per pixel inside the floor-casting pipeline. No extra assets, no extra setup.

water {
    color #1a6f92     // the body of the liquid
    wave 0.55         // 0 = glass flat, 1 = rough sea
    reflect 0.7       // how much sky it mirrors
}

map {
    "############"
    "#P...~~....#"
    "#.##.~~.##.#"
    "#...C~~....#"
    "############"
}
PropertyDefaultWhat it does
color#1a6f92The deep-water tint. Everything under the surface blends toward this color.
wave0.5Swell amplitude — how aggressively the sample coordinates are displaced each frame.
reflect0.65Sky reflection strength. Far tiles mirror the sky and fog color more strongly, like real grazing-angle water.

Water is not just visual — it is physical and scriptable. Wading in slows the player to 55% speed, plays the splash sound, adds a small camera nudge, tints the screen blue while you swim, and fires two world rules you can hook:

rules {
    on enter water {
        sound splash
        say "The water is warm and slow."
    }
    on exit water {
        say "Back on dry stone."
    }
}
Design tip. A moat around the exit, a flooded basement, a river the enemies won't follow you across (they can — but you're faster on land) — water reads as both beauty and gameplay. Pair it with ceiling off so the surface has a sky to reflect.

§Lighting & sky new in 1.1

v1.1 replaces the old flat-distance shading with a real lighting pass. Every pixel of wall and floor is lit by up to six nearby light sources, each with distance falloff and per-source color. The player always carries a soft warm lamp, and any sprite with glow on becomes a light: torches, crystals, glowing enemies, the exit portal itself.

item "torch" {
    char "t"
    shape torch
    color #ff9f43
    pickup off     // decor: never picked up
    glow on        // emits light with a flame flicker
}

Light is flickering — each source pulses on its own offset sine, so a corridor of torches breathes instead of humming flatly. The pickup off property (new in 1.1) turns any item into pure decor: it stays in the world, ignores the player, and still lights the room. Barrels, mushrooms and skulls love this too.

Two game settings complete the atmosphere kit. fogcolor tints the distance haze separately from the sky, and ceiling off swaps the ceiling for an open gradient sky with a parallax starfield — the sun never sets in a votyer game, but the stars do twinkle:

game "Surface Outpost" {
    size 960 560
    sky #0b1026
    fog 0.4
    fogcolor #0d1524
    ceiling off     // open sky + stars
    stars on        // twinkle (default on)
}
Performance note. Lighting is computed per wall column and per floor block, not per pixel — it stays fast even on modest hardware. If you need more headroom, lower detail before you remove torches.

§Items

Items are pickups: crystals, coins, medkits, keys, treasure. Each item declaration is a blueprint; every occurrence of its char in the map spawns one instance. Items bob gently, glow, and are picked up automatically when the player walks within half a tile.

item "crystal" {
    char "C"
    shape crystal
    color #5eead4
    value 25
    glow on
    on take {
        score += 25
        sound pickup
        if items left > 0 {
            say "Crystal! " + items left + " to go."
        } else {
            say "That was the last one!"
        }
    }
}
PropertyWhat it does
charThe map character that spawns this item.
shapeSprite shape — see the shape reference. Defaults to crystal.
colorBase color of the sprite.
valuePoints awarded by the default pickup behavior (used only when there is no on take handler).
glowDraws a soft colored halo. Defaults to on.
on takeA handler block that runs when picked up. If present, it replaces the default behavior — you decide what happens.

Handlers are where votyer comes alive. Inside on take you can change variables, play sounds, show messages, and make decisions with if. Two queries are especially useful here: items left counts every untaken item in the level, and items count "crystal" counts untaken items of one kind — perfect for quest logic.

§Enemies

Enemies are living obstacles. They patrol randomly until they can see the player, then chase. Touching one drains health and triggers the on touch enemy rule. You can also shoot enemies — each has hit points, takes damage from the blaster, flashes white on impact and dies with a satisfying descent.

enemy "stalker" {
    char "S"
    shape robot
    color #f59e0b
    speed 2.0      // tiles per second — faster than the player!
    sight 8        // how far it can see you, in tiles
    hp 25          // two blaster hits
    damage 25      // health drained per touch
    on hit {
        shake 0.2
    }
}
PropertyDefaultWhat it does
speed1.2Chase and patrol speed. Keep it below the player speed (3.0) unless you enjoy pain.
sight6Detection radius. Enemies also need line of sight — walls block their vision.
hp30Hit points. The player blaster deals 10 damage per shot.
damage15Health lost when the enemy touches the player. Touches have a 1 second invulnerability window.
on hit—Runs every time this enemy takes a blaster hit.

You can create new enemies at runtime with the spawn command, which clones a blueprint at a map position — useful for ambushes triggered by item pickups. Dead enemies trigger the on enemy dead rule once each, so kills can be scored or narrated.

§The exit

The exit is a portal sprite that ends the level. It starts locked by default: walking into a locked portal plays a denied sound and tells the player what is missing. When every item has been taken, the portal unlocks automatically with a rumble — or you can open it manually from any handler with unlock exit. This makes classic quest loops trivial to express: collect the crystals, then escape.

exit {
    char "G"
    color #8b5cf6
    locked on
}

When the player walks into an unlocked portal, one of two things happens. If you wrote an on reach exit rule, it runs and you decide the outcome — maybe the exit is a trap, maybe it needs a key. If there is no rule, the engine simply plays the win sound and shows the victory screen. Both paths fire the on win event, where you can display a final message.

§Rules

Rules are world-level cause and effect — they observe what is happening in the simulation and react. They are declared together in one rules block, and each trigger fires at most once per event occurrence:

rules {
    on all items taken {
        sound unlock
        say "The exit portal hums to life!"
    }
    on touch enemy {
        shake 0.4
        say "Keep away from me!"
    }
    on enter water { sound splash }
    on exit water  { say "Drip." }
    on reach exit  { win }
    on bump wall   { say "That is a wall." }
    on enemy dead  { score += 50 }
}
TriggerFires when…
on touch enemyAn enemy makes contact with the player (rate limited by invulnerability frames).
on all items takenThe last remaining item is picked up. The exit also auto-unlocks at this moment.
on reach exitThe player steps into an unlocked exit portal.
on bump wallThe player walks into a wall (once per second at most).
on enemy deadAn enemy loses its last hit point.
on enter water 1.1The player steps onto a ~ tile from dry land.
on exit water 1.1The player steps off a ~ tile back onto floor.

§Events

Events are handler blocks declared at the top level with on. Unlike rules, events hook into the game's lifecycle rather than world happenings:

EventRuns…
on startEvery time the game starts or restarts — after the title screen, before the first frame. Use it for mission briefings and timed hints with wait.
on tickOnce per frame during play. Use it for ambient logic — a clock, a chase timer, growing pressure. Keep it light.
on winRight after a victory is registered, before the win screen is drawn.
on loseRight after health reaches zero, before the game-over screen.
on start {
    say "Collect all 6 crystals."
    wait 2.5 { say "Beware the stalkers — they are fast." }
    wait 5   { say "Find the violet portal to escape." }
}

§Statements & commands

Inside any handler block you can use the full statement set. Statements run top to bottom, and blocks nest, so if can contain more if, wait can schedule any mix of statements, and so on.

Variables & assignment

score and health exist from the moment the game starts. Create your own with let, and update anything with =, += or -=:

on start {
    let combo = 1
    let target = 100
    score += 10
    health -= 5
    combo += 1
}

Commands

CommandEffect
say "text"Show a message toast at the bottom of the screen for ~3 seconds.
sound namePlay one of the ten built-in synth sounds — see the sound reference.
shake 0.4Screen shake with the given intensity (0 to 1.5).
win / loseEnd the game in victory or defeat immediately.
unlock exitOpen a locked exit portal with a rumble sound.
heal 25 / hurt 10Modify player health directly (capped at 100). Reaching 0 triggers defeat.
spawn "guard" 9.5 7.5Create a new enemy of the named blueprint at tile coordinates.
log "debug"Print to the browser console — your debugging best friend.

Control flow

if items left == 0 { unlock exit }
else { say "Keep collecting!" }

if health < 30 and health > 0 { say "You are badly hurt!" }

repeat 3 { log "pulse" }

wait 2 { say "Two seconds later..." }

Conditions support and, or and not, plus all the comparison operators. repeat runs a block a fixed number of times right now, while wait schedules its block to run after a delay in seconds — timers keep running through pauses, which makes them great for staged tutorials and delayed traps.

§Expressions

Anywhere a value is expected you can write an expression. votyer has numbers, strings, hex colors, booleans and variables, and the usual arithmetic with standard precedence — multiplication binds tighter than addition, parentheses group, and + concatenates strings when either side is a string.

ExpressionValue
2 + 3 * 414
"Crystal! " + items leftCrystal! 5 — numbers auto-convert
score / healthLive engine variables, readable everywhere
timeSeconds since the current run started
items leftCount of untaken items in the whole level
items count "crystal"Untaken items of one kind
random 6A random integer from 0 to 5 — dice, ambushes, chatter
health == 100, items left > 0Booleans for if conditions

§JavaScript API

Prefer to drive votyer from JavaScript instead of script tags? The runtime exposes a small API on the global Votyer object. This is how the playground on this site works — it compiles editor text and boots it into a canvas on every click:

// compile a votyer program without running it
const result = Votyer.compile(source);
if (result.ok) {
  result.spec;   // the resolved game blueprint
  result.ast;    // the abstract syntax tree
} else {
  result.errors; // array of human-readable error strings
}

// compile AND boot into a canvas (selector or element)
const game = Votyer.run(source, "#game");

// the returned engine (when ok) is a live game:
game.state;     // 'menu' | 'play' | 'pause' | 'win' | 'lose'
game.destroy(); // stop the loop and remove all listeners

// other exports
Votyer.version;         // "1.0.0"
Votyer.lex(source);     // raw tokens
Votyer.sounds;          // ["blip", "pickup", ...]

If compilation fails, Votyer.run draws the error message directly onto the target canvas — with line and column numbers — so players and you see what went wrong even with the console closed. A failed run returns an object with an errors array instead of an engine.

§E# for websites new in 1.1

votyer builds games. Its sibling language E# (files end in .e#) builds websites — complete, polished, responsive HTML pages compiled from a few readable lines. E# and votyer are designed as a family: an E# page can embed a live votyer game as one section, so your landing page and your game ship together, in the same tooling, with zero build steps.

Drop esharp.js on your page (next to votyer.js), then write E# inside a <script type="text/esharp"> tag with a data-target pointing at an iframe — the compiled site is rendered into it. Or call ESharp.compile(src) from JavaScript and do whatever you like with the output HTML string.

<script src="esharp.js"></script>

<iframe id="preview" style="width:100%;height:640px"></iframe>

<script type="text/esharp" data-target="#preview">
site "Nova — Design Engineer" {
    theme { accent #7c6cff  bg #0b0d17 }
    hero {
        title "I build products that feel alive."
        galaxy on
    }
}
</script>

How an E# file is shaped

Every file starts with site "Title" { and contains sections. A section is a name, an optional label, and a block of key value lines. Values are quoted strings, #hex colors, numbers or bare words. Repeat a key to make a list — three link lines make three nav links. One-line sections like theme { ... } are legal when they fit.

The galaxy on hero flag embeds a self-contained spiral-galaxy particle background with the same follow-and-spread mouse physics as the votyer site — no external scripts needed. Compiled output includes responsive design, scroll-reveal animations, smooth anchor scrolling and Open Graph meta tags automatically.

§FAQ

Is this really 3D?

It is true first-person 3D rendering using the classic raycasting technique — the same family of math that powered Wolfenstein 3D. The world is flat, but corridors, depth, sprites and fog are rendered in genuine perspective, column by column, at 60 fps.

Where does the WebGL come in?

The galaxy background on this site is a live particle simulation, and the engine composites through hardware-accelerated canvas. votyer's renderer is deliberately written against the 2D canvas API for maximum compatibility — it runs everywhere HTML5 runs, including locked-down school laptops and old mobile browsers, with zero shader-compiler surprises.

Can I use my own images or music?

Not yet — votyer v1 is intentionally asset-free so that games are single, portable HTML files. Procedural sprites and synth audio keep every game self-contained. Image textures and custom audio are the top candidates for a future version.

How big is the engine?

Around 100 KB raw, roughly 25 KB gzipped — smaller than most favicon payloads — and it contains the complete language, renderer, audio synth and UI. There are no dependencies of any kind.

Why another language?

Because the fastest way to learn game development is a language that only speaks games. votyer removes everything that is not level design: no DOM, no event listener plumbing, no asset pipelines. You write what the world is and what should happen; the engine handles rendering, physics and sound. When you outgrow it, every concept — entities, events, collision, game loops — transfers directly to bigger engines.
